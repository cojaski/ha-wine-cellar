- **v2.16.1** (published as a GitHub release): fixed the cabinet-grid visual bug where the grid's corner poked outside its golden zone background — root cause was nested `border-radius` geometry (`.cabinet`'s 12px outer radius with 8px padding needs an inner radius ≤ 4px; `.grid-inner` had 8px). - **v2.16.2** (in progress 2026-08-30, not yet released) — a cluster of rollbacks/refinements to `jamespreid`'s import plus new features, all user-driven:
  - `jamespreid`'s uniform-bottle-sizing feature (commit `f156995`, `targetCellPx`/`_targetGridWidth()` in `cabinet-grid.ts`) was fully reverted — cabinet grid sizing/layout is back to exact v2.15.0 behavior. The v2.16.1 border-radius fix (8px→4px) was reverted along with it (back to 8px) since it only mattered for the sizing feature's geometry — the user explicitly asked for a "total rollback", not a partial one.
  - Manual Vivino refresh (`ws_refresh_wine` in `websocket.py`) no longer always overwrites `type` — reverted to fill-empty-only for that one field, since two different wines (e.g. a producer's red and rosé of the same cuvée) can share a name and a refresh matching the wrong Vivino result must not flip a type the user already set correctly. `region`/`country` stay always-overwrite (user wants fresh data there on manual refresh). Batch refresh's existing fill-empty-only behavior was untouched.
  - Confirmed the AI/French-language search feature (from an earlier merge — `gemini.py`'s `_language_prefix`/`_language_suffix`) is live, then added a `description_language` tag (`Wine.description_language` in `models.ts`) stamped whenever an AI/Vivino description is written. `_build_ai_updates()` and the Vivino-refresh description-copy loops now regenerate the description if it's empty, has known-bad scrape text, **or** its stored language tag doesn't match the currently configured metadata language — including wines with no tag at all (pre-dates the feature), which are treated as a mismatch rather than assumed correct (the initial version got this backwards and silently regenerated nothing for any existing wine — fixed same day).
  - New cross-duplicate-bottle propagation: `_INSTANCE_ONLY_FIELDS` + `_propagate_to_duplicates()` in `websocket.py`, wired into all 7 wine-update call sites (manual field edit, Vivino refresh, AI analyze single/batch, Vivino batch refresh, auto-enrich). Any bottle sharing the same `name`+`winery`+`vintage` as the one just updated gets the same non-instance fields copied onto it — so refreshing/analyzing one bottle of a wine updates every other bottle of it too, instead of having to repeat the lookup per bottle. Excluded (stays per-bottle): `id`, `cabinet_id`/`row`/`col`/`zone`/`depth` (location), `price`, `purchase_date`, `added_at`, `notes`. `barcode` is deliberately **not** excluded — identical bottles share the same product barcode. **`vintage` itself is never part of `updates` from any AI/Vivino path** (confirmed by inspection — it's only ever read to build search queries), and since it's part of the propagation match key, different vintages of the same wine are treated as distinct wines and never share a description/rating/etc. — both by design, per the user's explicit concern that a 2022 and a 2023 can genuinely taste different.
  - `notes` was meant to be opt-in-only: a `propagate_notes` flag on the `wine_cellar/update_wine` websocket call, with the frontend (`wine-detail-dialog.ts`) supposed to `window.confirm()` before setting it when a duplicate exists. That confirm never actually fired for the user in testing (root cause not yet found — possibly a stale build, not re-diagnosed since it stopped mattering). **Net effect the user actually gets — notes always stays on the one bottle — is what they wanted anyway** ("la note reste individuelle sur chaque bouteille ce qui est logique en soi"), so this was deliberately left unfixed rather than chased further. If someone later wants working opt-in propagation, start by checking whether the compiled bundle on device actually contains the `propagateNotes`/`window.confirm` block in `_saveFields()`.
  - One earlier round of this same session's edits to `websocket.py`/`wine-cellar-card.ts`/`wine-detail-dialog.ts` reported a successful `device_commit_files` write that, per the user's next test, had not actually taken effect (re-reading the device copy afterward confirmed the old code was still there) — re-applied and re-verified by re-staging and grepping the device copy directly after commit, which is now the standard to follow: **don't trust a `written` result alone for a change that changes user-visible behavior; re-stage and grep/read the file back once before telling the user it's ready to test.**

## Key technical findings from recent work (don't re-discover these)

- **Vivino's `www.vivino.com/api/explore/explore` search API silently ignores the `q` param** for unauthenticated requests — returns the same generic "trending wines" list regardless of query (verified live, repeatedly). The relevance check that used to guard it let trending wines through whenever they shared a grape name with the query, writing the trending bottle's price/rating/photo/`vivino_id` onto unrelated wines (user saw many wines valued at "$1819", 2026-10-04). **`search_wine()` no longer calls the explore API at all** — HTML scrape only, which does real text search and has every field except price. Don't reintroduce it for its prices: they were never the searched wine's.
- **`api.vivino.com` (the mobile-app-facing backend) is open and unprotected** — no auth, no special headers, plain `GET https://api.vivino.com/wines/{id}` / `/vintages/{id}` / `/grapes/{id}` / `/foods` all work. Used for reliable refreshes once a wine's `vivino_id` is known (`VivinoClient.get_wine_by_id`). It has **no search endpoint** (by-id lookup only) and **no price data anywhere** — confirmed via extensive live testing (explore API, HTML scrape, real browser navigation, mobile API, even `curl` with browser-identical headers). Vivino's real price is not reliably scrapable; AI estimation (with user consent) is the fallback.
- A `Vivino Batch failed` bug turned out to be a websocket schema validation error (`ai_fallback` param sent by the frontend but not declared in the backend schema) — always check HA logs (`Paramètres > Système > Journaux`) for exact errors before guessing.
- LWIN / Liv-ex was investigated as a wine-ID/pricing source and **rejected**: the free LWIN database has no price/rating data (identification only), and Liv-ex's price data (Wine Matcher, Automation) is a professional fine-wine-trade product, not viable for this project.
- **Vivino's real cellar sync (reading/writing the user's own cellar) is possible via `www.vivino.com`'s Inertia.js endpoint using a pasted session cookie** — from `los7702`'s work, merged into this repo as of v2.15.0 (see "Current state" above). Untested against a real account so far.
- **iOS Safari blocks the live camera when the page is reached over `http://` (not a secure context) — confirmed on `dobunzli`'s own setup; worth checking whether this user's HA is also reached over plain http.** Not a secure context ⇒ Safari does not expose `navigator.mediaDevices` at all ⇒ `getUserMedia` throws a `TypeError`. No code fix exists; `label-camera.ts` detects it up front and offers the file input, which carries `capture="environment"` and opens the native camera with no secure context needed. If this doesn't reproduce for this user, it's because they're on https — good, nothing to do.
- **Camera errors must be told apart by `err.name`, never `err.message`.** Safari's denial message is "The request is not allowed by the user agent or the platform in the current context" — it contains neither "NotAllowed" nor "Permission", so substring matching on the message sends every iOS failure to the generic branch. Shared helpers live in `frontend-src/src/utils/camera.ts`.
- **Barcode scanning cannot work on iOS at all**: WebKit does not implement `BarcodeDetector`. Unrelated to the http/https question — even over https it reports "not supported on this browser". Unblocking it needs a WASM decoder (zxing) — ask this user whether that dependency is worth adding before spending time on it.
- **`hass.data["lovelace_resources"]` does not exist and never has** — that wrong key is why card auto-registration could silently do nothing, which is upstream issue #1 ("Custom element not found"). The collection is at `hass.data[LOVELACE_DATA]` (a `LovelaceData` dataclass, `.resources`) on current HA, or a plain `hass.data["lovelace"]` dict on older ones. Two traps around it: `async_items()` does **not** load the store (`ResourceStorageCollection` defers until a write), so an existence check reads empty and duplicates the resource on every restart — call `_async_ensure_loaded()` first; and YAML-mode dashboards have no `async_create_item` at all, so registration is impossible there by design.
- **Which add path calls what** (measured by `dobunzli` 2026-08-22, rebalanced in PR #29): barcode hit ⇒ Vivino only; barcode miss ⇒ falls through to the label; label photo ⇒ AI, *plus* a non-blocking Vivino lookup fired after the details step opens; search by name ⇒ Vivino only. Before #29 the label path never touched Vivino at all, so photo-added wines had no rating and **no `vivino_id`**, which also barred them from the cheap by-id refresh. The background enrichment only ever fills gaps and never overwrites the AI's reading, the user's photo, or name/winery/vintage — and it checks the candidate really is the same wine, because Vivino answers every query with something.
- **Vivino latency, measured by `dobunzli` with production headers**: the explore API takes 1.1–1.7 s and returns ~910 KB for five results; grape lookups are 0.06–0.2 s each. AI label recognition is a single call, no retry, 45 s timeout — that wait is entirely the AI provider's (check what this user's own provider/relay is if optimizing this path), so there is nothing to optimise on our side beyond not lengthening it. Requests that are independent now run concurrently (`lookup_barcode`'s two barcode DBs, grape names). `search_wine` is a single HTML request since the explore API was dropped (2026-10-04), so its old `fetch_extras` flag is gone too.
- **Occupancy and placement math is shared, not re-derived**: `frontend-src/src/utils/location.ts` owns the notion of a *container* (a bin, a box, the bottom zone, or one grid slot with its depth) plus usage, labels, next-free-depth and multi-bottle planning. `utils/suggest.ts` (where a new bottle should go) and `utils/arrange.ts` (what is untidy) both build on it. It previously existed in four diverging private copies.

## Branch / PR workflow

One branch per feature/fix, tested by the user on Synology, then PR + merge on the fork. **Branch from `main`, not from wherever you happen to be standing** — starting a second feature without checking out `main` first silently stacks it on the previous unmerged branch (happened once; fixed with `git rebase --onto main <old-base> <branch>`, plus a bundle rebuild, since the compiled JS then contained code the branch's sources no longer had).

**Several branches open at once is a deploy problem, not just a review one**: each carries its own compiled bundle and its own `FRONTEND_VERSION`, and the user can only run one on the Synology. When they pile up, merge them and hand over a single rebuilt bundle from `main` rather than asking for several deploys. Resolve the inevitable `const.py` / bundle conflicts by **rebuilding**, never by taking one side — a bundle picked from one side no longer matches its sources. After pushing a merge commit, GitHub needs ~10–20s to recompute mergeability; `gh pr merge` fails with "not mergeable: the merge commit cannot be cleanly created" until it does. Wait and retry rather than believing it. For genuinely large sessions, group related changes into a small number of themed PRs rather than one-per-tiny-fix (discussed and agreed with the user) — but if PRs are stacked (PR B based on PR A's branch), **do not delete branch A when merging PR A** (`gh pr merge --delete-branch`) until PR B has been retargeted/merged — deleting a stacked PR's base branch auto-closes it on GitHub. Retarget or merge in the right order instead.
